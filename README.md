## サービス概要

「言語化ジム」は、相手に合わせて分かりやすく説明する力を鍛えるトレーニングアプリです。

ユーザーは **「テーマ」** **「相手」**を設定し、相手に合わせた説明を入力します。

入力した説明をAIが分析し、説明の分かりやすさや構成、専門用語の使い方などについてフィードバックを行います。

自分の説明を客観的に振り返り、改善を繰り返すことで、相手に伝わる説明力を身につけることを目的としています。

## 開発背景

前職でお客様に商品の説明をしている時に、同じ内容で説明をしていても、伝わっている時と伝わっていない時があると感じることがありました。

その経験から、「誰」に説明するかで難易度が大きく変わることに気づきました。

実際に、お客様の年齢や知識、関心のあるポイントなどによって、説明する順番や言葉の選び方を変えることで、反応が良くなったり、質問が減ったりすることがありました。

その後、プログラミングを学習する中でも、同じような難しさを感じました。

自分では理解しているつもりでも、いざ人に説明しようとすると、

* どの順番で説明すればよいか分からない
* 専門用語を使いすぎてしまう
* 自分の説明が相手に伝わっているか分からない

といったことがありました。

そこで、**「相手に合わせて分かりやすく説明する力」を練習できる環境があれば、言語化力を高められるのではないか**と考え、「言語化ジム」を開発しました。

## ターゲットユーザー

主なターゲットは、 **自分の考えや知識を相手に分かりやすく言語化することに苦手意識を持つ人**です。

例えば、

- 学習した内容を人に説明する練習をしたい人
- 質問や報連相を上手くできるようになりたい人
- 専門知識を相手に合わせて説明する力を身につけたい人
- 自分の説明が分かりやすいのか客観的に確認したい人

などを想定しています。

## 差別化ポイント

### 「誰に説明するか」を設定できる

一般的な言語化トレーニングでは、提示されたテーマについて文章を書く形式が考えられます。

「言語化ジム」では、 **説明するテーマだけでなく「説明する相手」も設定する**ことで、相手に合わせて説明することを意識したトレーニングができます。

例えば同じ「MVP」というテーマでも、

プログラミングを全く知らない人
プログラミングを学習中の人
エンジニア

では、使う言葉や説明の順序が変わります。

このように、実際のコミュニケーションを想定して説明することを重視しています。

 **「伝え方」にフォーカスしたAIフィードバック**

AIには説明する相手・テーマ・説明内容を渡し、内容そのものの正誤だけではなく、

分かりやすさ
説明の構成
専門用語の使い方
相手に合わせた表現

など、 **説明の伝わりやすさ**を中心にフィードバックさせています。

## 技術的な工夫・こだわった点

### AI APIの利用回数制限

AIフィードバック機能ではOpenAI APIを利用しています。

ユーザー数や利用回数が増加すると、APIの利用制限やコスト増加につながる可能性があるため、 **Redisを利用してユーザーごとのAI利用回数を管理し、一定回数を超えた場合にAIフィードバックを制限する仕組み**を実装しています。

これにより、APIの過剰利用を防ぎ、限られたリソースの中でもサービスを運用できるようにしています。

### AIフィードバックの評価軸を「伝え方」に限定

AIによる評価では、説明内容そのものの正確性ではなく、 **相手にとって分かりやすい説明になっているか**を重視しています。

AIによる事実確認や専門的な内容の正誤判定には限界があるため、サービスの評価対象を「伝え方」に絞ることで、IT・日常生活・学習内容など幅広いテーマで利用できるようにしています。

### AIへの入力情報を整理

AIによるフィードバックでは、

- 説明する相手
- 説明テーマ
- ユーザーが入力した説明

をAIへの入力情報として利用し、単純に文章だけを評価するのではなく、**「誰に対して説明した文章なのか」**を考慮したフィードバックを行うようにしています。

## 開発について

### GitHubを利用した開発フロー

機能ごとにGitHub Issuesでタスクを管理し、Issue単位でブランチを作成して開発しています。

基本的な流れは以下の通りです。

Issue作成
  ↓
ブランチ作成
  ↓
実装
  ↓
Pull Request作成
  ↓
GitHub ActionsによるCI
  ↓
確認・修正
  ↓
mainへマージ
  ↓
Renderへデプロイ

### 小さな単位で機能を実装

一度に多くの機能を変更するのではなく、IssueやPull Request単位で作業内容を分け、変更範囲をできるだけ明確にすることを意識しています。

これにより、問題が発生した際にも原因となった変更を特定しやすくしています。
